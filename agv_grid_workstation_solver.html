Preferred path: hand the mission to the fleet supervisor on the Linux laptop (run it with --listen) — it dispatches natively with lower latency, the BUSY-ack protocol, and the same conflict + vision gates. The browser Start above is the fallback. Drive mode picks how the supervisor moves each robot once a mission starts: Color sensor + camera safety dispatches the original FORWARD_UNTIL_<color>/turn command vocabulary, with vision only monitoring/veto (the long-proven path). Camera only dispatches pure AprilTag position/heading control (drive_leg/turn_to_heading) and never uses the color sensor at all. Chosen per mission, sent with it — no supervisor restart needed to switch. Turn+drive fusion is DISABLED — built 2026-07-31 to skip the brake/settle between a turn and the following drive, but caused two real hardware collisions the same day (the arrival square-up after a fused turn+drive pointed the wrong way, since it only knew the heading it had just driven, not the heading of the leg after that). The supervisor forces it off unconditionally regardless of what's sent here. See turn_then_drive_leg()'s docstring in camera_grid_navigate.py for the full history before ever re-enabling it.
